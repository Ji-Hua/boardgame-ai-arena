## P-01：形成完整源码与运行依赖处置清单

### 1）做什么
建立每个版本、未提交路径、服务和数据根的去向，覆盖 AC-01、AC-03、AC-05、AC-06。

### 2）怎么做
刷新 GitHub refs、双机 status/worktree 和服务清单；逐项比较祖先关系及独有差异，包括 feature/backend_ai、旧 v0 仓库、training 的 decision-lab/web/app.js 和归档中的未完成合并。将源码、文档、产物、未知内容分别登记。检查 compose 挂载、systemd、定时器、进程 cwd、软链接及可访问的其他启动管理器；未访问范围明确列出。
产出 source-disposition 和 runtime-dependencies 清单，记录主机、路径、提交、状态、替代依据、依赖和拟去向；不能用目录年龄代替差异判断。

### 3）验收标准
- 每个已发现仓库/worktree 和未提交路径有归属；独有提交均有比较结论。
- 所有现行服务能映射到源码/镜像、环境、配置与数据；未知依赖标出影响范围。
- 无法判断的内容进入保全和待决清单，不默认删除或合并。

### 4）依赖其他步骤
无；需要 GitHub 与双机只读访问。实施开始时重新检查访问和基线漂移。

### 2）怎么做

扩展现有发布及回滚覆盖 Gameplay、Lab、Jobs、研究平台、gateway、两类 worker 和必要 MLflow 配置，保留现有单写入者及镜像隐私边界。对 Lab 固定旧镜像做兼容判断，优先以整合提交构建自有组件。记录第三方基础镜像例外。

## P-04：完成隔离功能、数据兼容和回滚演练

### 2）怎么做
复用现有模块测试、构建和 scripts/verify_stack.sh 的隔离机制，使用独立端口、数据副本和单独 Jobs 控制器。实际测试组织遵循测试规范，本计划不预写夹具或断言。

## P-07：归档旧源码并退役旧启动配置

### 2）怎么做
